# 0.2 Health checks и graceful shutdown

## Контекст

OrderFlow скоро поедет в Kubernetes: 3 реплики за Service, rolling update при каждом деплое.
Kubelet будет опрашивать liveness и readiness пробы каждого пода. Сейчас есть только общий `/actuator/health`, и опереться k8s не на что.

Зависимости приложения: Postgres, Redis, Kafka и внешний платёжный провайдер (WireMock на `localhost:8089`, эндпоинт `GET /health`).

## Требования

1. **Пробы.** `/actuator/health/liveness` и `/actuator/health/readiness` доступны при локальном запуске, а не только внутри k8s.

2. **Kafka health indicator.** Spring Boot не даёт готового индикатора для Kafka, пишем свой.
   - Ответ не дольше 2 секунд, даже если брокер недоступен (не висим на дефолтных таймаутах клиента).
   - Не создаёт новое подключение к кластеру на каждый вызов.
   - В `details`: `clusterId` и количество брокеров.

3. **Payment provider health indicator.**
   - `GET {base-url}/health`, connect- и read-таймауты заданы явно.
   - `base-url` и таймауты задаются через `@ConfigurationProperties` с валидацией (приложение не стартует с пустым URL).
   - В `details`: латентность ответа в миллисекундах.

4. **Группы.** Распредели индикаторы (`db`, `redis`, `kafka`, `paymentProvider`, `diskSpace`, `ping`, `livenessState`, `readinessState`) по группам liveness и readiness. Индикатор может не входить ни в одну группу.
   Решение оформи в `docs/adr/0001-health-groups.md`: для каждого индикатора укажи, в какой он группе и что произойдёт со всеми тремя подами, если эта зависимость ляжет на 5 минут.

5. **Graceful shutdown.** При SIGTERM приложение перестаёт принимать новые запросы, дожидается текущих (не дольше 20 секунд) и корректно закрывает ресурсы.
   Для проверки сделай эндпоинт `GET /api/dev/slow?ms=...`, который существует **только** в профиле `dev`.

6. **Со звёздочкой.** Пробы трёх подов раз в 5 секунд плюс Prometheus и мониторинг — это постоянный фон запросов к платёжному провайдеру. Реши, нужно ли что-то с этим делать, и если да — сделай.

## Критерии приёмки

- [ ] `./mvnw verify` зелёный
- [ ] Юнит-тест Kafka-индикатора: брокер недоступен → `DOWN` не дольше чем за 2 с (тест это проверяет, а не просто ждёт)
- [ ] Тест payment-индикатора на WireMock внутри JVM: `UP` при 200, `DOWN` при 500, `DOWN` при задержке больше read-таймаута
- [ ] Интеграционный тест: liveness и readiness возвращают 200 и `UP` при поднятых контейнерах
- [ ] Ручная проверка через `docker compose stop kafka` и `docker compose stop payment-provider`: HTTP-статусы и состояния групп совпадают с ADR (результат допиши в ADR)
- [ ] Ручная проверка shutdown: запускаешь jar, отправляешь `slow?ms=10000`, посылаешь SIGTERM → запрос завершился с 200, новый запрос в это время не принят, в логах видно ожидание
- [ ] В коде нет захардкоженных URL и таймаутов

## Куда копать

- `management.endpoint.health.probes.enabled`, `management.endpoint.health.group.<name>.include`
- `AbstractHealthIndicator`, `Health.Builder`; как Boot формирует имя индикатора из имени бина
- Kafka: `AdminClient` / `KafkaAdmin` из spring-kafka, `describeCluster()`, `DescribeClusterOptions`; какие настройки клиента отвечают за таймауты
- HTTP: `RestClient`, `ClientHttpRequestFactory` и где у него таймауты
- `server.shutdown`, `spring.lifecycle.timeout-per-shutdown-phase`; что Boot делает с `ReadinessState` при закрытии контекста
- WireMock в тестах: `org.wiremock:wiremock-standalone`, `WireMockExtension`. Его версией Spring Boot BOM не управляет, пропиши её сам в `<properties>`
- SIGTERM: при запуске из IDE кнопка Stop может слать не то, что ты думаешь. Проверяй через `java -jar` и `kill <pid>`
- Для пункта 4 представь: платёжный провайдер лёг на 5 минут. Что должно происходить с подами и с запросами на создание заказа? А если Postgres?

## Вне рамок задачи

Деплой в k8s (4.4), circuit breaker и ретраи (2.3).
