## 0001. Распределение health-индикаторов по группам liveness и readiness



Статус: принято

Дата: 2026-09-26



## Контекст



Приложение развернуто в Kubernetes в виде Deployment из **трех реплик (подов)**. Обновление происходит по стратегии **Rolling Update**. 
Система имеет зависимости: Postgres (хранилище), Redis (кэш/сессии), Kafka (асинхронные события) и внешний платёжный провайдер (REST Client).



## Варианты



### Относительно внешнего платёжного провайдера (`paymentProvider`):
*   **Вариант 1: Включить в группу `readiness`.**
    *   *Плюсы*: Пользователи гарантированно не попадут на под, который не может провести платеж.
    *   *Минусы*: При падении провайдера **все 3 пода** вылетят из балансировки. Kubernetes покажет `503 Service Unavailable` на весь сервис. Каскадный отказ: Rolling Update полностью заблокируется, так как новые поды никогда не станут «ready».
*   **Вариант 2: Вынести за рамки групп liveness/readiness (Оставить в общем `/health`).**
    *   *Плюсы*: Приложение остается доступным для других действий (просмотр истории, личный кабинет). Сборка и деплой (Rolling Update) работают независимо от аптайма внешнего API.
    *   *Минусы*: Запросы на проведение платежей будут сыпать ошибками `5xx` на живых подах. Требуется ловить деградацию внешними метриками.

### Относительно брокера `kafka`:
*   **Вариант 1: Включить в группу `readiness`.**
    *   *Плюсы*: Если под завязан на синхронную обработку данных из Kafka при старте, мы не пустим на него трафик, пока сеть не поднимется.
    *   *Минусы*: Если Kafka упадет глобально, все поды перейдут в `NOT READY`. Приложение, которое могло бы отдавать статику или читать кэш, полностью «умрет» для клиентов.




## Решение



| Индикатор | Группа | Почему |
|---|---|---|
| **ping** | `liveness` | Базовая проверка, что JVM жива и отвечает на простейшие HTTP-запросы. |
| **livenessState** | `liveness` | Внутреннее состояние Spring. Если приложение переходит в `BROKEN`, K8s должен его перезапустить. |
| **readinessState**| `readiness`| Внутреннее состояние Spring. Позволяет вручную (через события) плавно выводить под из балансировщика (например, при graceful shutdown). |
| **db** (Postgres) | `readiness`| Без БД приложение не способно выполнить ни одного базового действия. Под без БД не должен получать трафик. |
| **redis** | Вне групп | Используется для кэширования. При падении Redis приложение может работать напрямую с БД (деградация с потерей перформанса, но сохранением работоспособности). |
| **kafka** | Вне групп | Асинхронное взаимодействие. Если Kafka лежит, поды должны копить сообщения в локальной памяти (или возвращать ошибку очереди), но продолжать обслуживать веб-запросы пользователей. |
| **paymentProvider**| Вне групп| Внешнее API. Мы не имеем права связывать доступность нашего микросервиса с чужим аптаймом. |




## Сценарии отказов



1\. Платёжный провайдер недоступен 5 минут →

*   **Пробы на всех 3 подах**: `/liveness` -> `200 OK` (`UP`), `/readiness` -> `200 OK` (`UP`). Общий `/health` показывает `DOWN`.
*   **Что сделает K8s**: Ничего. Все поды остаются в балансировщике и продолжают работать.
*   **Что увидит пользователь**: Сайт открывается, авторизация и корзина работают. При попытке оплатить заказ пользователь получает красивую ошибку: *«Платежный шлюз временно недоступен, попробуйте позже»*.

2\. Postgres недоступен 5 минут →

*   **Пробы на всех 3 подах**: `/liveness` -> `200 OK` (`UP`), `/readiness` -> `503 Service Unavailable` (`OUT_OF_SERVICE`).
*   **Что сделает K8s**: Исключит все 3 пода из Service Endpoints. Новые поды не перезапускаются, старые не убиваются, но трафик на них блокируется.
*   **Что увидит пользователь**: Системную ошибку `503 Service Unavailable` от Ingress-контроллера (Nginx/Traefik).


3\. Kafka недоступна 5 минут →

*   **Пробы на всех 3 подах**: `/liveness` -> `200 OK` (`UP`), `/readiness` -> `200 OK` (`UP`).
*   **Что сделает K8s**: Ничего. Поды остаются live & ready.
*   **Что увидит пользователь**: Веб-интерфейс работает без изменений. Действия, требующие отправки событий (например, отправка email-уведомлений или пушей через Kafka), встают в очередь или завершаются внутренней ошибкой, но ядро системы доступно.


4\. Что было бы, попади db в liveness →

*   **В случае падения Postgres**: Все 3 пода одновременно провалят `/liveness`.
*   **Что сделает K8s**: Начнет циклически и бесконечно **убивать и перезапускать все поды** каждые несколько минут (`CrashLoopBackOff`).
*   **Результат**: Вместо мирно ожидающего сеть приложения мы получим колоссальную паразитную нагрузку на CPU/Memory нод Kubernetes из-за постоянного холодного старта тяжелых Spring Boot приложений. Если во время падения БД начнется деплой, приложение полностью сотрет старые поды и застрянет на старте новых.


\## Последствия


*   **Что стало проще**: Повысилась общая доступность системы (High Availability). Внешние сбои (Кафка, платежка) больше не «складывают» сервис целиком. Rolling Update работает предсказуемо.
*   **Что стало сложнее**: Логика обработки ошибок. Приложение должно уметь корректно обрабатывать ситуации, когда платежка или Kafka лежат (делать retry, показывать адекватные сообщения на UI).
*   **Риски и их компенсация**: Так как `paymentProvider` вынесен из readiness, мы рискуем слать запросы «в никуда». 
    *   *Чем ловим деградацию*: Мы внедряем **Circuit Breaker** (например, Resilience4j) на `RestClient` к платежному провайдеру, а также настраиваем алерты в Prometheus/Grafana по метрикам HTTP-ошибок (`rate(http_requests_total{status=~"5.*"}[1m])`).




## Проверка фактом



После применения конфигурации групп в `application.yml` были проведены тесты в изолированном окружении:

1.  **`docker compose stop kafka`**:
    *   `/actuator/health/liveness` -> вернул `200 OK`, статус `UP`
    *   `/actuator/health/readiness` -> вернул `200 OK`, статус `UP`
    *   *Ожидания совпали*: Система проигнорировала сбой брокера для внешнего трафика.
2.  **`docker compose stop payment-provider`**:
    *   `/actuator/health/liveness` -> вернул `200 OK`, статус `UP`
    *   `/actuator/health/readiness` -> вернул `200 OK`, статус `UP`
    *   *Ожидания совпали*: Сервис остался доступен в структуре сети.
